\section*{Abstract}\addcontentsline{toc}{section}{Abstract}
Mandate Wallet combines owner-approved financial delegation, x402 service procurement and separately verifiable purchase evidence. A fixed-owner, fixed-asset smart account atomically reserves shared task and session budgets before a client exposes a token-payment signature. The selected token calls the account's ERC-1271 validator at settlement, so revocation and policy replacement affect outstanding unpaid authorizations. A local gateway presents bounded MCP tools to Claude Desktop, Claude Code and Codex, while the owner reviews administrative transactions in an external wallet.

This document specifies the deployed route, its message domains and state transitions, the durable recovery implementation, and the exact distinction between a signed observation and independently established source truth. It develops the three research directions from the team's previous proposal into an implementation-oriented account of policy-bound actions, delegated-session accountability and host interference. Formal properties are accompanied by assumptions and manual arguments rather than a claim of machine verification.

The public demonstration uses native Claude Desktop, Rabby and Base Sepolia. It pays 0.01 test USDC once, recovers an injected service failure using the same order and settlement, and rejects an unused step after owner-signed session revocation. A separate evaluation records 120 eventual HTTP tasks, 132 settlements without duplicate payment, and 10,000 distinct explicitly invalid contract calls. The independent public-case verifier passes its required financial checks but retains an incomplete overall report. Independent HTTPS provenance, complete unobserved history and isolation from the local administrator remain outside the demonstrated guarantee.\citep{case,eval,repro}

\section{Product scope and research contribution}\label{sec:introduction}
\subsection{The user problem and a concrete task}
A tool-capable agent needs a way to purchase a service without receiving unrestricted control over its owner's assets. A prompt can describe a budget, but the financial boundary must survive a host that ignores that prompt or calls the signer directly. Mandate therefore places the amount, recipient, approved-step and lifetime constraints in the purchasing account. Tool permissions and connection credentials govern access to the local application, while chain state governs spending authority.

The running task asks Claude to purchase an ETH statistics sample and produce a short brief. The root budget is 150000 atomic USDC units, the per-payment maximum is 100000, and the sample costs 10000. At six decimals these correspond to 0.15, 0.10 and 0.01 test USDC. ETH names the dataset, not the asset being transferred. The fixed result is \code{datasetId=mandate-fixed-fixture-v2}, \code{asset=ETH}, \code{count=3}, \code{mean=110}. It has no market timestamp, price unit or live-price guarantee.\citep{case}

The owner creates the root policy and a finite session in the workspace through Rabby. Claude reads the account context, obtains the approved service's quote and calls the bounded purchase tool. After payment, the merchant deliberately returns HTTP 500. A second call recovers the original paid order and returns the sample. Finally, the owner revokes the session and the next approved-but-unused service step fails before registration. This one case exercises authority, settlement, delivery, recovery and withdrawal of future permission.

\subsection{What the release contributes}
The implementation brings together a two-level conservative reservation ledger, registered-digest-only contract signatures, business-step idempotency across agents and policy versions, durable x402 recovery, native agent integration and a verifier with explicit evidence grades. The engineering contribution lies in this concrete combination and its reproducible failure cases. The document does not claim that scoped smart accounts or delegated wallets were invented here.

The previous proposal organized research around policy-bound execution, minimum delegated-session evidence and host-interference bounds.\citep{proposal} The release instantiates these directions with a narrower procurement route. A research objective in that proposal is not evidence that a corresponding mechanism has been deployed. In particular, a mandatory on-chain session-root proof, a universal legacy-web proxy, independent paid-merchant TLS attestation, globally enforced model-query limits and beacon-bound anti-grinding are not current release features.

\subsection{Related work and positioning}
Programmable validation and modular account interfaces provide the context for Echo's UserOperation route.\citep{erc4337,erc7579,erc7702} Mandate's selected service-payment route instead connects typed registration messages to the token's contract-signature callback. The precise token implementation matters because a transfer-authorization interface alone does not ensure contract-signature support.\citep{erc1271,erc3009,x402compat}

Scoped agent accounts already exist. Safe documents agent spending limits and multiple-agent configurations, while MetaMask documents granular delegated permissions.\citep{safe,metamask} These capabilities preclude a blanket assertion that competing wallets enforce every policy only off chain. The comparison in this project is therefore a controlled EOA/Mandate experiment, not a market-wide security ranking.

Acharya studies agent authenticity and transaction intent using a proposed hybrid framework.\citep{acharya} BAID concerns user--code binding and reports an implemented prototype using code-level authentication.\citep{baid} Identity and execution provenance are complementary to Mandate's finite payment scope. The release does not implement their proof systems or derive its security from agent identity registries. ERC-8004 identity metadata is a possible future integration, not an input to the present authorization predicate.\citep{erc8004}

TLSNotary supplies a possible independent source-evidence primitive, while drand supplies publicly verifiable external randomness.\citep{tlsnotary,drand} Neither substitutes for request binding, budget accounting or evidence retention. The release's optional TLSNotary experiment concerns a separate public API with a same-host notary/prover. Beacon-bound commitments remain research work.
