# Mandate Wallet 总体建设方案

版本：0.3

更新日期：2026 年 10 月 15 日
团队：Mandate Labs  
参赛方向：Topic F Agent Wallet  
状态：M1—M5 已验收；T9/T10 全部完成，G1/G2/G4 关闭，正式子项 97/105。M6 保留 T8.07/08/10 的人工钱包体验及剩余路径，G3 开放；M7 已交付技术报告、幻灯片、实际演示及源码候选，T11.08 材料核查已完成，T11.01/02/09 继续。

Mandate Wallet 让现有 AI Agent 能按用户授权采购服务。用户先确认预算、商户和有效期，再签署 Mandate。Agent 只能在这些权限内付款，用户可以查看采购结果，并通过独立验证器核对执行记录。

项目既要解决 Agent 采购的实际需求，也要验证付款约束是否可靠，并留下可复现的研究结果。Echo 是实现基础；原研究提案中的授权、会话证据和宿主干预问题，则是研究工作的起点。开发按任务依赖和验收条件推进，本方案不估算工期，也不分配人员。

具体任务、状态和验收清单见[实施任务清单](IMPLEMENTATION_TASKS.zh-CN.md)。

持续开发的轮次与授权边界见 [Goal 执行说明](GOAL_EXECUTION.zh-CN.md)。M4 的实际 Agent 客户端接入和所有者操作状态流程已验收；M5/T7 已经全部验收。M3—M7 的任务映射已列出，后续实现沿用原依赖。主网采购和正式比赛提交等待用户明确授权，测试网与材料准备继续推进。

M1 已完成 T2，确认了 Base Sepolia 原生测试 USDC、已部署 ERC-1271 原型与自建参考 facilitator 的组合。原 Echo 7702 路线不兼容此次 EIP-3009 采购；主网与第三方 facilitator 仍需分别实测。以下问题按当前证据和后续任务继续跟踪：

1. 继续使用 Echo 的 EIP-7702 委托账户，还是采用已有智能账户基础设施并安装 Mandate 模块。
2. Base 上指定 USDC 实现、账户 ERC-1271 验签和选定 facilitator 能否完成受约束的 x402 支付。
3. 链上登记单次授权与预算预留的方案，如何处理撤销、过期、并发和不确定结算。

## 3 产品形态与用户流程

### 3.1 产品组成

| 组成 | 交付形式 | 主要责任 |
| --- | --- | --- |
| Mandate Agent 插件 | MCP Server 和 Skill，按宿主客户端包装 | 给 Agent 提供结构化工具和使用流程 |
| Mandate Gateway | 本地运行服务，后续可提供经过验证的远程部署 | 服务发现、报价处理、支付构造、状态协调和证据生成 |
| Mandate Web App | 浏览器控制台 | 用户授权、审批、撤销、查看任务、付款和证据 |
| Mandate 协议 | 账户模块、授权和预算合约 | 在已验证的付款路径上，检查并执行预算和收款范围等规则 |
| Mandate SDK | TypeScript 库、CLI 和示例 | 让其他 Agent 和应用接入同一套接口 |
| Mandate 官网与文档 | 产品网站、开发者文档和安全研究页面 | 解释产品、提供接入资料并公开验证结果 |

MCP 提供工具接口，Skill 指导 Agent 使用流程。资金约束由确定性代码和合约执行。宿主客户端的工具批准机制仍然适用。

Codex 和 Claude Code 的接入方式参考[Codex MCP 文档](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)和[Claude Code MCP 文档](https://code.claude.com/docs/en/mcp)。首版验证两个客户端，不默认所有支持 MCP 的平台行为一致。

### 3.2 主场景

用户提出任务：

> 完成一份指定主题的数据分析报告。可以购买必要的数据 API，总预算 2 USDC，单次最多 0.2 USDC，仅使用已批准的服务。新增商户先询问我，授权今天到期。

目标流程：

1. Agent 澄清需求，列出任务计划和可能需要的付费资源。
2. 控制台把授权转换为清晰的字段，用户检查并签署。
3. Agent 通过 Bazaar 搜索服务，系统筛选网络、资产、价格、服务范围和付款兼容性。
4. Gateway 从实际端点获取最新报价，验证资源、收款人和报价来源。
5. 系统检查授权并登记必要的支付承诺，Agent 完成 x402 请求。
6. 系统分别确认链上付款、服务返回和结果是否满足预设检查。
7. Agent 交付报告，附实际支出、剩余额度、引用来源和证据。
8. 用户可以撤销剩余权限，或用独立验证器检查证据包。

初版接入现有 Agent。站内可以提供同一流程的演示入口，但不要求用户迁移到我们自建的聊天产品。

### 3.3 权限分层

- 读取公开报价、余额和授权状态：按连接权限提供查询。
- 已批准 Mandate 内的采购：允许协议支持的自动执行。
- 新增商户、扩大预算、改变资产、延长期限或修改账户控制权：提出用户审批请求。
- 暂停、撤销和恢复：由明确的账户控制权限执行。若增加 guardian，其权限只能按规格收缩授权，不能扩大支出权。

Agent 的请求、用户已签署的授权和链上实际生效状态必须分别记录。生成待签交易不表示授权已经生效。

复用前应完成源代码复核：

- 把 UserOperation 中的可复用 bearer secret 改为对操作及授权上下文的数字签名。
- 统一 delegation module、decoder、gateway 的 ABI、selector 和金额字段。
- 检查输入资产限制、原生币 value、执行模式、slippage 和残余 allowance。
- 区分验证、预算预留、执行成功和真实支出。
- 校验 UserOperation 成功状态和实际代币变化，不能只依据交易哈希判断任务完成。
- 更新文档中与代码不符的账户模型、IntentRegistry 和日志说明。

这些是源代码检查发现和实施前置任务。运行结果由 T1 重新建立，不能使用 README 中的测试数量代替当前测试结果。

每个环境需要独立的部署地址、RPC、区块浏览器、资产地址、EntryPoint 或 delegation 配置、facilitator 能力和测试证据。不能直接复制 Sepolia 的地址或假定服务商在各网络提供相同能力。

CDP 文档列出 Base 和 Base Sepolia 支持，动态能力应检查 `/supported` 和实际结算。[Facilitator 文档](https://docs.cdp.coinbase.com/x402/seller/facilitator)

### 5.2 x402 的授权边界

常见 x402 结算由 facilitator 调用代币合约或 Permit2，不一定经过 Echo 的 `validateUserOp`。因此，MCP 层检查通过不能证明所有支付路径都具有链上预算保护。

M1 已在指定公共测试网组合验证：先登记支付摘要和预留金额，再由已部署钱包的 ERC-1271 验签确认该摘要的权限状态，最后由原生 USDC 结算。首版采用 exact／EIP-3009 路线；具体支持范围与撤销证据见 [M1 兼容性矩阵](M1_COMPATIBILITY.zh-CN.md)。

[钱包兼容性文档](https://docs.x402.org/advanced-concepts/wallet-compatibility)描述了 EIP-3009、Permit2 和不同账户的验签差异。ERC-7710 作为候选扩展路径单独评估，不能仅凭规范描述就宣称已有生态支持。参考[exact EVM 规范](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_evm.md)。

兼容性矩阵至少记录：网络、代币实现、账户实现、支付方法、签名格式、facilitator、SDK 版本、预验证结果、实际结算结果和撤销行为。不支持的组合必须有明确的产品行为。

### 5.3 Bazaar 服务发现

[Bazaar](https://docs.cdp.coinbase.com/x402/buyer/discover-services)是服务发现来源。目录数据用于筛选候选资源，实际付款条件以端点的最新响应为准，并与已签授权核对。

服务记录需要包含资源 origin、路径和方法、收款地址、网络、资产、协议版本、价格、支持的扩展、schema 和最近可用性。若验证商户签名，还需建立资源与签名者的授权关系。

新增商户可以被发现和推荐，但不能自动扩大已有 Mandate。受控探索模式需有用户明确批准的金额和服务边界，作为后续功能。

### 5.4 多链预算

初版使用用户签署的按链预算分配。每条链独立执行其额度，界面汇总支出和预留。跨链共享预算、自动桥接和跨链原子性不属于初版。

链 ID、钱包、资产和验证合约参与签名域或授权摘要，业务标识也包含必要的网络上下文。主网集成测试使用单独资金和预设总额，在前置验证通过后开展。

## 6 授权与预算模型

### 6.1 核心对象

| 对象 | 必须表达的内容 |
| --- | --- |
| PolicySpec | 用户、Agent、钱包、网络、允许操作、商户和服务范围、预算、期限、版本和撤销状态 |
| ActionProof | 授权引用、业务标识、具体支付或 calldata 摘要、金额、资产、收款人、nonce、有效期和付款前证据引用 |
| SessionAttestation | 会话身份、委托范围、记录承诺、来源类型、披露规则和证明者信息 |
| ContainmentDecisionLog | 允许／阻止／终止等决定、规则依据、证据引用和签名 |
| PaymentCommitment | 支付摘要、预留额、有效期、支付授权 nonce、政策版本和保守的结算状态 |

ActionProof 初版可以由签名和必要的证明数据构成，不默认已经使用零知识证明。自然语言目的先转换为用户确认的机器可检查字段，不能把自由文本解释直接当作链上安全保证。

### 6.2 权限状态

授权建议经历草拟、待用户签署、生效、暂停、撤销和到期。Agent 可以提出草案和变更请求，不能自行扩大已签权限。预算降低和撤销如何影响已登记、未结算支付，必须在规格中明确，并在实际 token 验签路径上测试。

用户主密钥始终属于可信授权边界。Agent 使用有限权限的会话签名能力，接口不暴露无限制的签名、转账或权限修改工具。

### 6.3 预算不变量

核心安全目标是：

> 已确认支出与所有尚可执行或结算不确定的支付承诺，合计不得超过该任务的链上分配预算。

支付前先登记必要的预算承诺。ERC-1271 验签本身不能负责修改累计预算，不能依赖单次验签解决并发超额授权。

实现必须区分保守占用额度和已证明的真实支出。若链上只能确认 nonce 已使用，不能未经论证就推断它一定表示某次成功付款；不同代币的取消和使用状态可能需要进一步解释。结算数据不足时继续保守占用额度。

释放金额必须证明该承诺尚未支付且已经不能执行。候选条件包括经验证的 nonce 状态与链上到期状态。不能仅因为 HTTP 超时、Agent 声称失败或本地进程重启而释放。

初版保持资产单位明确，使用 USDC 原始整数单位进行计算。Gas、服务费和 API 费用分别说明由谁承担及是否计入用户预算，不默认 gas 免费。

### 6.4 业务幂等和结算状态

支付记录至少区分报价、预算占用、授权发出、结算待确认、已付款、服务已返回、结果检查、确定失败和安全释放。

业务幂等标识应来自明确的任务步骤、请求和商户订单关系。链上 nonce 防止同一授权再次结算，业务标识处理同一订单被包装为新授权的问题。对于本来允许重复购买的 API 调用，应由任务规格区分合法重复和错误重试。

付款交易、服务返回和结果质量是不同状态。RPC 或 facilitator 返回哈希后，仍需检查交易、相关事件和网络确认状态。拒绝的签名或 bundler 模拟不一定产生持久链上事件，报告保留相应的链下拒绝证据。

## 7 证据与宿主干预

### 7.1 证据的时间顺序

付款前记录请求和报价，生成付款前的证据承诺。ActionProof 绑定这个承诺。付款和服务返回后，再生成包含交易和回执的完成证据，关联同一个 intent 和任务。

付款前的证明不能包含尚未发生的服务返回，也不能把未来回执的哈希当作已经验证的事实。采用会话检查点和追加关系，避免循环哈希依赖。

### 7.2 证据来源

| 来源 | 能支持的判断 | 需要说明的条件 |
| --- | --- | --- |
| 本地记录和 Merkle 承诺 | 披露记录与承诺一致 | 记录的真实性和完整性仍依赖采集方 |
| 商户签署的报价和回执 | 被授权签名者作出了相关声明 | 验证签名者与商户的绑定，不能单独证明质量 |
| 独立 HTTPS 见证 | 选定 HTTPS 内容的来源证据 | 明确 TLSNotary 等工具的兼容性和见证信任条件 |
| 链上交易和事件 | 对应网络中的实际支付或合约行为 | 明确代币地址、收款人、数额及确认策略 |

优先复用[x402 Signed Offers & Receipts](https://docs.x402.org/extensions/offer-receipt)，为不支持该扩展的商户标明证据等级。独立 HTTPS 见证先覆盖一个经验证的端点，不承诺支持所有网站。

请求体和授权内容使用必要的盐或其他隐私措施进行承诺，避免低熵内容被猜测。证据包默认不包含登录凭证、cookie、API key 或完整敏感响应。

### 7.3 宿主能力与保证边界

恶意宿主可以操纵 Agent、改变链下消息、延迟提交、删除本地记录和重复调用模型。研究假设它不能伪造用户主签名、破坏密码学或任意改变链上共识状态。

| 攻击 | 目标机制 | 能力边界 |
| --- | --- | --- |
| 重放和重复业务付款 | nonce、支付摘要和业务幂等状态 | 明确业务标识的可信生成方式 |
| 延迟提交 | 授权有效期和报价期限 | 拒绝过期执行，不能强迫宿主按时提交 |
| 隐藏任务失败 | 外部登记的任务义务和监测 | 检测预期结果缺失，不单凭缺失判断动机 |
| 删除证据 | 独立存储、检查点和承诺 | 承诺支持检测不一致，数据可用性需另行保障 |
| Grinding | 独立调用控制、承诺或可信执行环境 | 宿主可在控制器外调用模型时，无法限制所有隐藏调用 |
| 绕过会话代理 | 有限凭证、独立采集和必要的隔离 | 与 Agent 共处恶意宿主的代理，不能独立证明所有网络活动都受控 |

可信钱包签署界面、Agent 运行环境、Gateway、见证者和监测服务之间的边界必须明确。运行在同一台机器上不自动意味着隔离。界面和安全报告展示具体保证，不使用未验证的完全信任消除承诺。

## 8 科学问题与实验

### 8.1 原提案的研究目标

[原提案](../previous_proposal/Proposal_echo.tex)包含三个核心问题：恶意宿主下的 policy-bound execution、delegated-session accountability 的最小证据，以及 host-interference 的检测和防御边界。

| 研究方向 | Mandate 的研究产物 |
| --- | --- |
| 授权执行 | 形式化攻击者模型、授权和预算不变量、状态机、论证与反例测试 |
| 会话证据 | 证据字段规格、隐私与覆盖分析、独立验证器和披露实验 |
| 宿主干预 | 各攻击的可行性／不可行性说明、必要信任条件和复现实验 |

新增的集成研究问题是：异步 x402 付款在并发授权、重试、撤销和结算不确定时，如何维持任务预算与业务幂等安全。

协议实现提供实验平台，科学贡献需要由明确的性质、分析和比较实验支持。有限测试中没有错误接受，不等于一般性安全证明。

### 8.2 基线与消融

- 修复后的 Echo 基础，用于区分基础缺陷修复与新增机制。
- 普通 x402 客户端或选定现有钱包的可测试配置。
- 关闭证据关联的 Mandate，用于测量证据机制的贡献和开销。
- 完整 Mandate，使用同一任务集合和公开信任条件。

竞品测试仅在我们控制的账户和测试服务、或得到明确授权的环境进行。不能根据不同配置得出的结果宣称整个平台不安全。

### 8.3 评价指标

| 类别 | 指标 |
| --- | --- |
| 实用性 | 任务完成率、结果可用性、人工确认次数、恢复成功率 |
| 资金安全 | 错误接受、错误拒绝、超预算、重复付款和撤销后的付款 |
| 预算记账 | 并发承诺、结算不确定、释放后的状态与实际资产变化 |
| 证据 | 支付关联覆盖、独立验证成功、篡改检测和披露量 |
| 开销 | 实际服务费用、gas、额外交易、端到端延迟和 P50／P95 |
| 可复现性 | 固定版本、随机种子、配置、运行记录和原始结果 |

原提案提出至少 10,000 个无效操作样本和若干检测率目标。保留 10,000 样本作为初始 fuzz 实验目标，具体分布、样本单位和置信解释由实验规格确定。不得预先填入成功率或把设计目标当作测试结果。

已有 x402 安全研究需要进入相关工作和基线设计，包括[授权和跨层绑定研究](https://arxiv.org/abs/2605.11781)以及[facilitator 执行安全研究](https://arxiv.org/abs/2607.19545)。

## 12 初版完成标准与后续扩展

初版需要完成两种 Agent 的 MCP 接入、用户授权与撤销、Base Sepolia 的 x402 采购、至少一个经过验证的支付路径、预算与幂等测试、证据验证、完整网站和 App、SDK 示例及比赛材料。Ethereum Sepolia 提供复用基础的回归证据，Base 主网提供真实服务验证。

M2 的固定 Alto v0.7 严格路径存在返回值/trace 兼容缺陷，采用明确记录的四文件补丁（D-M2-04），保留全部严格验证规则；不能以 unsafe 模式结果代替验收。
