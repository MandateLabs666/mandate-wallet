# Mandate Wallet 总体方案

Mandate Wallet 为 Agent 提供范围明确、预算有限且可撤销的服务采购权限。所有者通过外部钱包批准任务及会话；Claude Desktop、Claude Code 或 Codex 通过本地 MCP Gateway 获取报价、执行获批步骤并恢复原订单。普通使用流程、开发接口及证据检查均围绕同一任务和付款记录展开。

## 产品与系统结构

智能账户固定 owner、token 与链。任务策略限定收款人、业务步骤、单笔金额、总预算及期限，会话只能在任务范围内进一步收窄权限。付款登记原子预留任务和会话预算，token 结算时通过 ERC-1271 检查最新权限。已付款、等待结算与结算不明的承诺继续占用额度；仅满足严格过期和 nonce 未用条件时才能释放。

Gateway 连接商户与 facilitator，持久化报价、原始付款意图、交易和服务状态。网络失败后先对账原操作，不生成新的业务 nonce 重付。官网、工作区及开户向导以统一的黑白、银灰和蓝色视觉展示真实状态；所有者管理签名保留在外部钱包。

## 研究方向

研究工作讨论授权意图如何绑定具体付款、哪些会话证据足以支持独立检查，以及宿主删改记录或绕过客户端时仍能保证什么。现有实现提供 typed payment、保守预算预留、关联检查点、选择披露与独立验证器，并以参考控制器测试有限的宿主干预边界。

签名只认证相应声明，不能自动证明外部来源真实。未知尾部记录和同宿主管理员隔离仍是限制。当前控制器只能限制经自身接口的调用。独立付费商户 HTTPS 见证、全局模型查询限制及基于未来随机信标的机制保留为研究扩展。

## 实施与验收

当前任务及剩余要求以 [实施任务清单](IMPLEMENTATION_TASKS.zh-CN.md) 为准，任务按依赖关系推进。产品规格、合约、服务、MCP、证据、Web、SDK、运维和开户向导分别保留自己的完成标准。已实现的功能、开发者自动检查、人工试用和独立审计分别记录。

研究比较采用相同 HTTP 任务的四组配置：普通 EOA、仅有链上约束的 Mandate、关联证据的 Mandate，以及加入参考控制器的 Mandate。实验定义见 [实验协议](M7_EXPERIMENT_PROTOCOL.zh-CN.md)，测量规则见 [测量说明](M7_BENCHMARK_DECISIONS.zh-CN.md)。具体结果从交易、余额、事件和独立进程记录重新核对。
